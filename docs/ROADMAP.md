# H.I.D.E 后续开发规划

> 定位：**轻量文本编辑器**。每项功能都要过"轻量"这道门槛：不显著增加包体积、不引入常驻后台、不让界面复杂化。
> 当前版本：v1.4.2（2026-09-23 发布：安卓外部「打开方式 / 分享」修复、两端「获取另一版」互引面板、
> 更新链国内镜像与多源回退、触屏取色入口 + 全编辑器通用选区工具条、手机顶栏脏点配色勘正）

## 版本策略

应用已完成正式发布，此后走 SemVer 常规节奏：**功能版挂主题、补丁版随修随发**。
每个版本只挂一个主题、功能项控制在三项以内，做完再规划下一版 —— 避免一次性铺太多摊子。

**v1.5 是对「≤3 项」的一次有意例外**（2026-09-23 定）：主题仍是设备互联，另挂 51（语言高亮）与
52②（弹窗层 48dp）两项收尾。理由与代价都写清楚：52② 搭车是因为互联要新写一批手机/平板界面，
48dp 实测那一轮本来就要做，拆开等于再上一遍设备；51 与主题无关，纯粹是它塞进补丁版会把发版拖长，
既然 v1.5 周期本来就长就一起走。**代价：本版发版周期显著长于以往，且中途不出补丁版**。
因此内部按阶段拆两次发布（见 v1.5 小节的「发布拆分」），不要把七件事攒到最后一个 tag。

历史里程碑：0.1.0 初始提交、0.2.0 安卓移植、0.3.0「及格线」批次、0.4.0 编辑体验、
0.5.0 差异化小功能、v1.0.0 正式发布（发布链路 + 工程化）、v1.1.0 可视化内容视图、
v1.2.0 大文件与跨文件检索、v1.3.0 结构化内容与新格式、v1.4.0 安卓全面触屏适配、
v1.4.1 触屏收尾补丁、v1.4.2 外部打开与更新链镜像。

## v1.2 —— 大文件与跨文件检索（P0）

主题：**把"打开任意文件"这条路径做到不翻车**。这是用户第一分钟就会遇到、也是同类轻量编辑器被抱怨最多的一环。
设计稿：`docs/superpowers/specs/2026-09-15-large-file-strategy.md`（三层分级：≤32MB 可编辑 / 32~512MB 只读分块预览 / >512MB 拒绝并给替代建议）。

27. ✅ **超大文件打开**（Rust `src-tauri/src/large_file.rs` + `src/lib/largeFile.ts` + `LargeFileViewer.tsx`）
    - probe 单次顺扫统计行数并构建自适应稀疏行偏移表（条目超 2M 步长翻倍稀释，内存 ≤ 16MB）；
      read_line_window 按行窗口读取（CRLF 剥离、超长行 1MB 截断、单窗口 4MB 预算）；UTF-16 按码元扫描换行
    - 前端虚拟滚动（滚动条代理映射 + sticky 行块，超浏览器布局上限按比例压缩）+ 换窗去抖防竞态 + 跳转行
    - 打开路由三层分级统一收敛：选择器 / 最近 / 文件树 / 拖拽 / argv / 会话恢复全部先查尺寸再决定
    - 编辑出口：提取当前窗口到可编辑新标签页；大文件标签不进外部文件监听（避免整读做 diff 基准）
28. ✅ **跨文件搜索**（Rust `src-tauri/src/search.rs` + `src/lib/dirSearch.ts` + `FileTreeSidebar.tsx` 搜索态）
    - `search_in_dir` 按需一次全量扫描（无索引、无常驻后台）：黑名单/隐藏目录与 symlink 跳过，
      >32MB 与二进制文件跳过并计数；逐文件复用既有编码检测解码，按行匹配（大小写/正则/全词，
      正则按行匹配且 regex crate 不支持 lookaround）；结果收集 1000 条上限、计数全量、扫描 2 万文件封顶
    - UI 为文件树侧栏内嵌搜索态（不新增常驻面板）：Enter 触发、分组列表 + 命中高亮 + 统计条，
      Esc/关闭回树；点击命中打开文件并定位行列（`FileTab.jumpRequest` → CodeEditor 挂载后居中选中；
      已打开的脏标签不重读磁盘直接定位）；安卓 SAF 无递归枚举，入口隐藏（regex 仅桌面依赖不进 APK）
29. ✅ **查找上限解除**（`src/lib/searchCore.ts`）：解除 200 万字符扫描与 5000 匹配上限——全量计数、
    「全部替换」走 `replaceAllInText` 全文一次替换不再截断；装饰高亮仍限 5000 条（CM6 渲染约束），UI 显示「共 N 处（仅高亮前 5000 处）」
30. ✅ **小地图大文件适配**（`src/lib/minimap.ts` + `CodeEditor.tsx`）：固定画布高度 + 超阈值停用语法着色 + 只绘制可见行窗口
    - 实测（本机 Edge/Blink 152 headless，与 WebView2 同内核；探针 `scripts/canvas-limit-probe.html` / `.ps1`，可复跑）：
      单个 canvas 单边上限 **65535 设备像素**（65536 起静默失效，与宽度 60~1000、面积至 6555 万像素均无关），
      且 **越界后的 canvas 元素永久失效**——缩回合法尺寸也画不出内容，只有新建元素才恢复；
      折算旧实现（行距 5px + 上下 padding 6px）= **1.31 万行 @dpr1 / 6.55 千行 @dpr2**，与既有文档「约 1.3 万行」一致
    - 旧实现每帧重设 `contentH = 行数 × 5px`，既必然越界（该标签页小地图此后永久空白）又每帧遍历全文行数；
      现在画布尺寸只由「容器可见高度 × dpr」决定（`minimapCanvasDeviceSize`，结构性保证永不接近上限），
      按 `computeMinimapMetrics` 只画可见行窗口（≈ 容器高度 / 行距 行 + 缓冲），绘制量与文档规模无关，

    `platforms.*.url` 指向 Gitee、以及桌面端应用内更新能从镜像清单里拿到合法签名

55. **桌面端「覆盖脏标签」的口子**（48 号顺带查出，本版只在安卓外部打开路径上避开）：
    `openPathIntoTab` 命中已打开的标签时直接用磁盘内容替换并清掉脏标记，
    而这条路径桌面有三处入口（文件树点击、最近打开菜单、二次实例 argv）。
    也就是说：在桌面改到一半没保存，再从文件树点同一个文件，改动就没了。
    修法与安卓侧一致（脏则只聚焦），但要动桌面行为、得配桌面回归测试

56. **「打开方式」还差两类提供方**：报 `application/octet-stream` 的管理器（`.svelte`/`.kts` 等冷门扩展）
    与直接给 `file://` 的旧管理器（无 MIME，任何带 mimeType 的 filter 都不匹配）。
    覆盖要声明 `*/*` 或纯 scheme filter，代价是在所有文件类型（含图片、压缩包）里出现，本版刻意不做

57. **外部打开的标签在应用被杀后可能恢复不了**：提供器只给临时授权时 `takePersistableUriPermission`
    会抛异常（已吞掉），本次进程内能读能存，杀进程后该 URI 失效、会话恢复会静默丢掉这个标签。
    待办不是「修好」而是**别静默**：恢复失败时给一条「上次从外部打开的文件授权已过期」的提示

58. **平板档文件树顶栏未重量**：50 号删掉了搜索入口，顶栏从三个按钮变两个；
    手机档已实测（两行排布不变形），≥768px 那一档是纯删项、风险低但没量过

## v1.5 —— 设备互联（局域网直连）

主题：**手机接着编辑电脑上的文件**。扫码连接，无账号、无云中继、不出局域网。
设计稿：`docs/superpowers/specs/2026-09-21-device-link-design.md`（方案层面的决策已全部收敛，见其第 2 节与第 12 节）。

三条已定的地基：**桌面恒为服务端、手机恒为客户端**（手机当服务端会被 Doze / App Standby 杀后台监听，
可靠性不可控；「存回桌面」由手机发起写请求实现，不需要手机监听端口）；**开关按需启停、不引入常驻后台**
（原写作「手动开关」，2026-09-23 按下方第 1 条改为「记忆并启动自动 bind」）；**二维码携带地址，
因此不做自动发现**（顺带避开 Android 组播锁 `MulticastLock` 与各厂商 ROM 差异、以及公司网 / 路由器 AP 隔离吞组播的问题）。

### 开工前的否决性实测（不写业务代码就能做完，做完才允许动阶段 0）

1. ✅ **release APK 能走局域网明文 TCP —— 已验，通**（2026-09-23，全量证据在设计稿 §11.2）。
   实测：Tab S8 上 **release 签名的 1.4.1 包**经「从网址导入」发起 `http_get`，本机 `0.0.0.0:8765`
   收到 `GET /probe-x ua="ureq/2.12.1"`。UA 是 ureq 而非 Chromium → 走的是 **Rust 原生 socket**；
   8765 不在任何明文白名单内 → **`usesCleartextTraffic="false"` 不约束 `std::net`**。
   为什么这条当初是否决性的：v1.5 手机主动连桌面，若明文限制是 **UID 级**（内核 eBPF 丢包），
   `std::net` 一样连不出去，七件事全部要重排 —— 现在不用重排。三条兜底（挑白名单端口 / 上 rustls TLS /
   放开 cleartext）全部不需要，留档备查。控制组同日早先也过了：`uid=shell` 的 `nc` 连同端口拿 200。

   即**同一进程内 Rust 放行、WebView 拦截**，不是「这台设备压根不执行明文策略」。

以及 `platform.ts` / `fileIO.ts` / `largeFile.ts` / `useFileActions.ts` / `FileTreeSidebar.tsx` / `App.tsx` 的分支。

三条与设计稿字面不一致的地方，都是实现时按「一件事只留一个口径」改的，设计稿不再回头改：

1. **换行符不进协议**（§4.2 的 `read` 载荷原本有 `eol`）。桌面侧 eol 的权威判据本就是前端的
   `detectLineEnding` + 落盘前 `applyLineEnding`，远程读取又走同一个 `openedFromDecoded`——
   服务端再算一份只会多出第二个口径，两份还可能不一致。所以 `read` 原样带回 CRLF，归一交给前端；
   `write` 收到的 `text` 已是调用方按 eol 还原过的最终字节。
2. **基线只用内容哈希，不带 `baseMtimeMs`**（§4.2/§5.4 写的是「hash + mtimeMs」）。
   mtime 判等在桌面刚保存过的那一秒内分不出新旧，拿它判等会**静默覆盖桌面的改动**；内容哈希不会。
   `mtimeMs` 仍在 `stat`/`read` 里带回，只用于展示。基线为空串的写入直接以 `badparams` 拒——
   没有基线就落盘等于毁数据。
3. **远程上限 6MB 而不是 32MB**。32MB 是桌面「只读分块预览」那条线，而 §5.3 明确不做远程分块预览，
   加上单帧 8MB 上限，超 6MB 的文件即使传过来也只能进一个既不能编辑又不能分窗读的死角
   （6MB = 编辑器 200 万字符可编辑线在 CJK 下的最坏字节数）。`stat` 照实报尺寸，`read` 以 `toobig` 拒。

**本轮查出的两条实现级事实**（都会反复用到）：

- **加一条 `#[tauri::command]` 要同时改四处**：`link.rs` 实现、`lib.rs` 的 `generate_handler!`、
  `build.rs` 的命令清单、`capabilities/default.json` 的 `allow-<命令名>`（`build.rs` 头部注释早已写明，
  本轮仍然漏了第三、四处）。只漏 `build.rs` 时它会 panic 并打印全部已知权限（很长，容易误读成 ACL 语法错）；
  **只漏 `capabilities` 时没有任何编译错误**，运行时表现为「link_set_root not allowed. Command not found」。
  是 `scripts/link-verify.mjs` 的 F 段把它当失败暴露出来的——这类「命令注册了但没授权」单测查不出来。
- **同一端口关共享后短时间内绑不回来**：`link_server_stop` 确实释放了监听（实测 `netstat` 无 LISTENING 残留，
  满足「关闭即释放端口」），但上一台设备的连接留在 TIME_WAIT 时，std 的监听套接字按
  `SO_EXCLUSIVEADDRUSE` 绑定会被直接拒——**实测 45 秒未散**，短重试救不了。
  按决策 §12.1-3「不许静默换端口」办成可操作文案（`bind_listener`）：说清是端口被占、等一分钟或换一个端口。

**验收判据里没做到的那一条**：「真机在共享根里打开一个 md、编辑、保存回桌面」——
本机两个 AVD（`phone35`、`aurora35`）客户机**完全没有网络路由**（`ping 10.0.2.2` 与 `ping 8.8.8.8`
都是 `connect: Network is unreachable`），拿它们跑局域网等于什么都没验，所以这一条**没有**在本轮冒充通过。
模拟器上做了两件与网络无关且确实会翻车的事：x86_64 debug 包装进 `aurora35`，① 页面入口脚本哈希
== 本轮 `dist/index.html` 的哈希（装的是这一版前端）；② `link_request` 在安卓侧回的是
「手机上还没有连着桌面」而**不是**「not allowed」，`link_set_root` 同样被授权——即上面那条四处登记的坑
在 APK 这一侧也过掉了。**真实 Android 客户端的局域网往返仍未验过**，留给阶段 3 连着桌面标签同步一起上真机。

### 阶段 3 收口记录（2026-09-24）：四条按实测改掉的口径与四条真 bug

**交付**：`link/board.rs`（进程级看板 + 根外白名单 + `@w/<id>/<名字>` 引用解析）、`link/board_tests.rs`
（15 例，四组安全用例**先写失败再实现**）、`fsrv` 的 `Scope` 化与 `tabs` 命令、`Msg::Event`
与服务端推送队列 `Push`、`link_report_tabs` 命令 + 四处登记、`lib.rs` 全局 `on_window_event`
（Focused / Destroyed）、前端 `hooks/useTabReport.ts`（节流 + 按可见变化去重）、`remote.ts` 的 @w 分支、
手机端 `RemoteTabsSheet.tsx`（portal 到 body、脏标签置灰）。

四条与设计稿字面不一致的地方，都是实现时按「一件事只留一个口径」改的：

1. **`tabOpen {index}` 取消，改用 `@w/<id>/<名字>` 引用**（§4.2 命令集里那条）。下标随开关标签漂移，
   手机上那份标签的身份键必须稳定；更要紧的是：按 index 开就得为它另写一套读/写/冲突判定，
   而 `@w` 引用能直接塞进 `hide-remote://` 的 rel 位，与根内文件**共用同一条通道**（含基线哈希与冲突）。
2. **白名单取所有活窗口的并集，列表只取聚焦窗口那一份**。设计稿 §6.1 只说「tabs 命令返回聚焦窗口那份」，
   若白名单也跟着只取聚焦窗口，用户在桌面 alt-tab 一下就把手机上**正在编辑**的那份文件抽走了。
3. **共享根改成按窗口存**（阶段 2 是全局一份）。多窗口下「最后挂载的窗口赢」是错的：
   手机看到的标签列表来自聚焦窗口，树却可能是另一台窗口的根 —— 两者必须同一份判定。
   连带效果：某窗口没开文件树 → 该窗口聚焦时只暴露标签（正是 §2 决策 3 的「没开树就只给标签」）。
4. **「根外额外暴露」只数根外**。白名单条目里根内根外混在一起（引用不能随聚焦窗口漂移），
   但设置面板那行说的是「根外多交出去几个」，含根内就虚报。

四条在真机之外被这轮实测查出来的真 bug（都已修，各自有回归用例）：

- **新开一个文档窗口会把手机上正连着的链路踢掉**：每个窗口挂载都跑一次「上次开着共享就自动 bind」，
  而 `link_server_start` 非幂等 —— 它 `replace_stop` 掉正在跑的那台。修法两条：自动开只由主窗口发起；
  `link_server_start` 对「同端口且已在监听」直接回当前状态。这条只有多窗口才会暴露，
  也正是「多开两个窗口才能验判定」这条判据的价值。
- **关窗后迟到的上报会把死窗口复活**：关窗流程会先收干净标签，那次上报可能落在 `Destroyed` 之后，
  于是看板里又有了那个窗口，还成了「最近动过的」—— 手机上凭空多出一份空列表。
  窗口存在与否只有 Tauri 知道（`window_alive`），不能在看板里记死标签：`win-N` 是**复用**的标签。
- **`PREFS_KEY` 里混进一个 U+2026 省略号**（`heid-l…refs`）：读写同一个常量所以功能看着是好的，
  但 `scripts/link-verify.mjs` G 段那句「先清掉 `heid-link-prefs.enabled`」一直在清一个没人读的键 ——
  那条防护从写下来就没生效过。H 段第一次跑到「reload 后服务端换到 47123」就是这个原因。
  代价：这台机器上「记忆开着共享」的状态因键名修正而回到关，需要重新打开一次开关。
- **`document.hasFocus()` 不能当窗口聚焦判据**：WebView2 在窗口失活后仍报告文档有焦点
  （实测：手机看到的明明是新建窗口的列表，主窗口 hasFocus 仍是 true）。改用 `plugin:window|is_focused`。
  另外 `set_focus` 没有被授权（也不该为测试授权），所以「主动切焦点」这条路在 H 段是走不通的。

**验收做到哪、哪一条没做**：`cargo test --lib link::` 84 例 + `npx vitest run` 84 文件 / 1040 例 +
`node scripts/link-verify.mjs` 74 项 PASS / 0 FAIL（H 段 14 项跑在真实应用上，含多开一个文档窗口的
聚焦判定、换根后同一标签改由 `@w` 寻址并在手机上读到逐字内容）。**没做到的一条**：
「真机在共享根里打开 md、编辑、保存回桌面」以及本轮的「手机看桌面标签并接着改」——
本机两个 AVD 都没有网络路由（阶段 2 那条结论仍然有效），而用户明确说本轮不必折腾真机，
所以**真实 Android 客户端的局域网往返仍未验过**，留给阶段 4 与实时更新一起上真机（届时由用户配合）。
H 段的聚焦判定在「两个窗口都不在前台」时会降级为「新建即切换 + 关窗回落」这一对，
降级时脚本会如实打一行说明，不会冒充成了字面判据。

三条按实测改掉的口径：

1. **链路撑得住，但靠的是两个机制各管一段，缺一个就被刷爆：黑名单管"依赖树在共享根里"，
   目录去重管其余**。`npm install` 形状过完逐层黑名单只剩 0.17%（264 条），整段推 **24 字节**；
   而用户把一棵不含黑名单目录的大树当共享根时，黑名单一点忙都帮不上（保留 53%，与不过滤的对照行
   只差 1.6×），那一格是**目录去重**把 15.7 万条事件压成 27 帧 / 70 KB / 峰值 4 帧每秒 ——
   相对单帧 8 MB 的上限与一次 6 MB 的文件读取，这不算瓶颈。**只判第一层也不行**：
   `npm install` 那格的第一层是共享根自己的目录名，只有逐层判才让子树在 `node_modules` 那一层被滤掉
   （只判第一层，保留比例从 0.17% 变 53%）。
2. **载荷只列「哪些目录的内容变了」，不列文件**（工单原文写的是 `changes:[…]` 文件清单）。
   表格最后一行就是按工单字面写完再量的结果，三条代价都在那一行：体积是目录版的 4 倍、
   29 帧里 16 帧撞条目上限被迫退化、以及为了分辨一个名字是文件还是目录（Windows 的通知不带类型）
   逐条 `stat` —— 一次合并 364.8 ms 里 stat 占 364.8 ms、序列化只占 0.1 ms，全程 3.8 秒。
   而手机端要做的两件事都不需要文件清单：树按「展开着的层在不在 dirs 里」重列，
   「我打开着的这个文件被桌面改了没」按「它的父目录在不在 dirs 里」判，命中再去 `stat` 比哈希，
   与阶段 2 的写冲突同一套判据（**内容哈希才是权威，事件只是「该去看一眼」的提示**）。
   代价如实记：手机端要多跑一次 `stat` 才知道是不是自己正看着的那个文件。
   上限因此按目录数定：实测单帧峰值 205 → `MAX_PUSH_DIRS = 256`、字节上限 32 KB，
   超了退化成不带载荷的 `event{type:'fs'}`（阶段 3 已有的「变了，去重取」语义）。
   换成只推目录之后**四个场景一帧都不必退化**。
3. **合并用定周期 flush（300 ms），不用拖尾去抖**。持续变更的那三格，拖尾式**全部只发 1 帧**
   而变更持续 11~29 秒 —— 事件不间断时它永远等不到那 300 ms 的安静，手机端整段不刷新，
   与「实时更新」字面相反。日常保存那一格两者都是 3 帧（事件之间本来就有 >300 ms 的间隔），
   也就是说定周期只在持续变更时更好、成本一样，没有理由用拖尾。

顺带量到两件以后还会反复用到的事实：
① **监听自身的成本可忽略** —— 递归 watch 建立 230~310 µs，跑完 15.7 万条事件之后探针进程
   工作集 18 MB、句柄 139 个（notify 在 Windows 上是**一个递归句柄**，不是每目录一个），
   所以「为互联多挂一份监听」与桌面文件树那份并存不冲突。
② **`canonicalize()` 在 Windows 上返回 `\\?\` 前缀路径，通知回来的路径会带着它一起拼** ——
   取相对路径必须按组件处理，不能按字符串前缀（阶段 2 的 `roots.rs` 早写过这条，本轮再撞一次）。
③ 改名实测一次产生 `rename-from` + `rename-to` 两条；「丢 from 只留 to」那条规则在日常保存那格
   被验证（21 条原始 → 20 条送去合并，丢的正是 from）。

**如实记下列到与没量到的**：
① 「`npm install` 形状」是把整份 `node_modules` 拷进 `根/probe-churn/node_modules` 复现的，不是真跑
`npm install`（真跑会改 `package-lock.json`）。文件数、目录深度与路径里的 `node_modules` 成分都与真装一致，
所以「过滤滤掉什么」这一项是按字面场景量的；差别是 npm 自己的临时文件改名与硬链接阶段没覆盖。
② 「可见目录」那两格是压力场景（13.4 万文件的变更放在一个不含黑名单目录的位置），远超本仓日常，
留它是为了定上限，不是为了说日常长这样。
③ **手机端收到帧之后重列的往返成本没量** —— 那是实现阶段的事，届时由 `scripts/link-verify.mjs` 量。
④ 帧的**延迟**这里也量不了（探针记的是事件时间戳）：定周期 flush 的墙上延迟按构造是
合并窗口 300 ms + 泵线程 `POLL` 20 ms + 一次 `list` 往返，真数等真机（工单第 5 条）。

等它打 `READY` 之后 `touch '<仓库>/probe-trigger'` 再制造变更；探针静默 5~8 秒自己收工。

### 阶段 4 收口记录（2026-09-24）：交付、四条按实测改掉的写法、以及本轮查出的三条真 bug

**交付**：桌面侧 `link/watch.rs`（`Batch`：逐层黑名单 + 链接点按目录缓存 + 定周期合并；

`link.rs` 的 `Push::queue_fs` + 出口合并（`fs` 那一类不套「同类型只留一条」，而是在 `take` 时
把攒下的目录并成一帧）、`EVENT_FS` / `EVENT_ROOT`、`sync_fs_watch`（监听随连接与聚焦窗口的根而生灭）、
`board_edit`（把"要不要通知对端"与"根换了没"收在同一次加锁里）；`Cargo.toml` 把 notify 从
dev 依赖提成桌面直接依赖（**不新增编译产物**：8.2.0 已随 tauri-plugin-fs 在树里）。
手机端：`lib/remoteChanges.ts`（事件名、载荷解析、求交判据、订阅入口）、
`FileTreeSidebar`「只重列受影响的那几层」+ 换根重建、`hooks/useRemoteFileChanges.ts`
（打开中的远程文件按"父目录命中 → `stat` 比哈希 → 变了才读"接进**桌面外部修改同一个**
`handleExternalChange`，因此时间线、采纳/忽略、脏标记语义全都沿用既有的那套，没有新造提示）。

四条与工单字面不同、按实测改掉的写法：

1. **载荷只列目录不列文件**（工单写 `changes:[…]`）—— 见上一节第 2 条，实测逐条 `stat`
   一帧 364.8 ms、体积 4 倍、60% 的帧撞上限。
2. **定周期 flush 而不是拖尾去抖** —— 拖尾式在持续变更期间一帧都不发。
3. **「桌面保存一次 = 手机端一帧」不成立**：Windows 把一次 `writeFileSync` 分成创建 / 写数据 /
   关闭时补尺寸几条通知，彼此间隔能越过一个合并窗口，真实应用上实测 3 帧、载荷是同一份
   `{"dirs":[""]}`。所以验收判据写成「个位数帧、载荷种类 ≤2」，
   而「有没有第二份监听在推」交给「换根之后旧根不再推帧」那条去夹 —— 那条才是真判据。
4. **换根推 `rootChanged` 而不是 `tabs`**：它是 `tabs` 的超集（手机端要丢树缓存、重列、再重取列表），

**本轮查出的三条真 bug**（前两条已修并有回归用例；第三条修在验收脚本里）：

- **`Push::take` 发完不清空目录集合** → 同一批目录每 20 ms 重发一遍，等于自己把链路刷爆。
  是 `fs_推送按窗口合并载荷且装不下就整体退化` 里那句「发过的不该重复发」先红才发现的。
- **监听建不起来时走了 `mark_error`**：一个只影响实时更新的附属失败（共享根被上一轮删了 /
  没权限 / 路径过长）会把 `connected` 一起打成 false，界面谎报"链路断了"，而读写一条都没受影响。
  现场是全量验收里 A、H 段各两条莫名其妙地红了 —— 关掉监听后 14/14 过，才定位到这里。
  修法：只往 stderr 记一行，不碰状态快照。

  连读了 5 轮都报"0 帧"，白查了三轮过滤器、监听与窗口状态。教训写进了那段代码的注释：
  判据同时含「该来的来了」和「不该来的没来」时，工具自己漏帧会让两类判据一起给出误导性的答案。

**这一轮查出来的三条**：

1. **重新配对（不是免扫重连）会让之前攒的条目永久卡住、而且完全静默**。`peerKeyId` 是那把 LS 的哈希，
   每次配对都重新生成临时 X25519 → keyId 换（实测同一台电脑两次配对得到
   `b8e5535d…` 与 `4f7ca381…`）。判据要保留（连着 A 不能把 B 上攒的改动写进 A 的同名文件），
   改的是不许默默卡住：一连上就出一条「有 N 份是攒在另一台电脑上的」，说清"连回那台会自动补上"，
   同一趟连接只提一次。**欠账**：要做成"换键也认得同一台"，得把 `hide-remote://` 的 deviceId
   从 LS 哈希换成长期身份指纹（§12.1-5 那个 fp），那会牵动已打开标签的身份键，单独一轮。
2. **冲突但标签没开着时，「查看差异」会开到一个空弹窗**：时间线的存活域是"被标签引用的路径"，
   重启之后远程标签恢复不了，那条红点就没有对应的差异可看。现在那句先说下一步
   （「打开它之后，在时间线里逐条采纳」），不开一个看起来像坏掉的空窗。
3. **`write` 的冲突回包原先无条件带上桌面正文**：桌面把文件改到 40 MB 之后，手机的一条待回放
   会撑断 8 MB 帧上限、把整条链路打死（后面所有条目一起失败）。现在超限只报"有冲突 + 尺寸 + 哈希"，
   手机据此走「给不出差异」那句，而不是摆一份空的「桌面版本」让人去采纳。
   顺带把二进制判定收成一个口径（`encoding::is_binary` 提为 `pub(crate)`），没在命令面另写一份采样。

    - 修法方向：渲染结果带 `finalUrl`，**`chrome-error://` 前缀直接判为失败返回 null**（信号现成，
      本次的错误页正文里就有这一行）；若静态正文同样过薄，就如实说「该页需 JS 渲染，
      安卓端渲染不支持明文 http」，别拿错误页冒充正文
    - 影响面如实界定：**只影响安卓 release + `http://` + 静态正文过薄**这一组合；
      `https://` 与桌面端都不走这条路。但 `http://` 是内网 / 本机调试地址的常态写法，不算边角

主题仍是设备互联，动机是他说的两件事：**扫码本身就是最快的连接动作，不该在电脑前再点一次允许**；
以及连上之后「桌面端的文档没发到手机上，文件夹树也是」。

**① 桌面那道 TOFU 确认整条撤掉**（`serve_conn` 的 `Mode::Pair` 不再等用户表态）：
`PairReq` / `EVENT_PAIR` / `pending` + `decision` / `wait_decision` / `link_pair_approve` /
`link_pair_deny` / `LinkStatus.waiting_confirm` 一并删干净（两端命令表、事件订阅、确认框 JSX、
`link.stateAwaitConfirm` 等 5 个文案键）。登记、落盘、界面上「谁连着」一步没省。
**票从不上网**，出示过票 = 用户亲手把码给出去了，这就是准入本身。

**② 顶掉这道确认的是新的握手失败限速**（`GATE_LIMIT=5` / `GATE_COOLDOWN=60s`，按来源 IP）：
不能只删不补 —— 6 位短码那趟的 salt 是短码本身（票 128 bit，短码约 20 bit），原先挡在中间的
正是那道确认。按 5 次 / 60 秒算，试遍 10^6 的期望耗时以年计；真用户一次就过，撞不到阈值。
**没报上过 `hello` 的连接不进账**（端口扫描、打印机探测不该把真手机挤在门外）。

**③ 桌面开着共享就自动续码**（`QR_REFRESH_MS=70s`，票 120 秒过期）：以前屏幕上那张码两分钟后就是死的，
用户得回电脑前点「换一个码」。换码走新的 `pair::PairingWindow` —— **窗里同时留着刚换下的那一张**，
手机相机正对着的码不会在换掉那一瞬间当场作废；`hello.slot` 因此扩成 `ticket:<票的公开标识>`
（标识 = SHA-256(票) 前 3 字节，推不回票；旧版手机与手输短码仍发光秃秃的 `ticket`/`code`，按当前那张认）。

**④ 手机连上之后直接落在「电脑上正打开的文件」那一屏**：`RemoteTabsSheet` 从设置里提到 **App 级唯一一份**，
扫一扫 / 粘贴配对码 / 短码 / 免扫重连四条路都开它（启动时的静默自动重连**不**开，不该抢走他正在编辑的东西）；
那一屏自己分三档说话：还在拨过去（「正在连上 X…」）/ 桌面拒了（把 `Refused.reason` 原话摆出来）/ 曾经连着现在断了。
扫一扫那颗不再弹「已连接」的 toast —— 落地的那一屏就是反馈。同一屏加了「浏览这台电脑的文件」入口，
整棵远程树一跳就到。手机连上后能看见什么仍取决于桌面那个根：**根没开就是空的**，这条在桌面「共享范围」那一行明示。

**实测（1280×800 模拟器壳 x86_64 debug 包 ↔ 本机 dev 桌面，全程桌面零点击）**：
- 自动续码：面板打开后 **48.7 s** 自己换了码（定时器从挂载起算，间隔 70 s），期间用户一次没点；
- 宽限期：把 **刚被换下的那张票**（`b10e7d…`）递给桌面 → `connected=true`，手机拿到桌面 3 个标签的列表；
- 内容：点开一行 → 手机上渲染出电脑上那份 markdown 的正文（状态栏 `hide-remote://…`，10.0 KB / 103 行）；
- 树：那一屏点「浏览这台电脑的文件」→ 侧栏列出桌面的 `link-test` 根（`nested` / `中文 名称.md` / `gbk.txt` …），
  浮层与那一屏同时收掉；
- 限速：连续错 5 次之后第 6 次拿到 `对端拒绝（slowdown）：这台设备配对失败的次数太多…`，
  再等 65 s 用新码正常连上（冷却会自己过期，不锁死真用户）。
验收：`cargo test --lib` 183 例（新增 6：配对窗 5 + 闸门 1）、`npx vitest run` 1186 例、`tsc --noEmit` 干净。

**这轮上机才撞出来的三条真 bug（都不在计划里，桌面单测与前端单测都测不到）**：
1. **免扫重连失败之后没有出路**：`isLinkEnabled(手机)` 原先按 `role === 'client'` 判"在用"，
   而启动时自动重连被拒之后 role 就停在 client —— 于是那一格只剩两颗灰掉的按钮，
   粘贴配对码 / 短码 / 手填全被藏起来，想改扫一张新码就没有路。改成按 `connected` 判。
2. **平板壳漏接落地屏**：`IS_ANDROID_APP` 才是"客户端那半栏"的判据，不是窗口宽度 ——
   1280 的壳走的是 `DeviceLinkMenuButton`，第一版只给手机顶栏那条路接了回调，
   于是粘贴 / 短码点了不落地。补上，并让浮层在掀开那一屏时自己收掉。
3. **早退的 `Refused` 到不了对端**：写完那一帧直接 drop，手机此刻已经把 `hello` 发出来了，
   带着未读数据关闭 → 对端收到的是 **RST**，那句人话一个字也没看见（实测冷却与 busy 两条路都这样）。
   新增 `refuse_and_close`：先 `shutdown(Write)` 再排空 200 ms，实测 slowdown 文案能完整到达。

**已知边角（本轮没动）**：同一台设备**一秒内**连续重连时，偶发（本轮 7 连发里 2 次）报
「Connection reset by peer」而不是原因 —— 快速重连时新旧连接的临时端口撞了，早于本轮改动，
真实操作节奏（看完报错再扫）碰不到。另外 `run_pump` / `sync_fs_watch` 里还留着 `[heid-fsDBG]` 那批
调试输出，每次推送都往 stderr 打一行，该单独收一次。

#### 2026-09-27 他上手第一天就撞回来了：自动续码放大了一个 race

他装到手机上（签名 release 原地升级）后点「刷新配对码」再配，手机报**「对端已关闭链接」**、
桌面报**「上次失败：帧解密失败：配对票不匹配，或链路已被截断」**。模拟器上按同一顺序复现成功
（两条串成对出现，只是方向相反）。

**根因是我这一轮自己带出来的**：`hello.slot` 有两种口 —— 带票标识的（新包扫码 / 粘贴 / 手填 32 位）
和**不带标识**的（手输 6 位短码，手机手里没有票值算不出标识；以及旧版手机全部走这一口）。
不带标识时桌面只能拿「当前那张」派生密钥。以前票只在用户手动点「换一个码」时才换，
「屏幕上那张 == 当前那张」几乎恒成立；**加了 70 秒自动续码之后换码变成后台行为**，
手机照屏幕上那张算、桌面照刚换过的那张算，两边握手都走完、密钥不同 → 报出来的就是
「帧解密失败 / 对端已关闭连接」这种看不出谁做错了什么的串。

三条一起改（缺一不可）：
1. **换码的判据收到服务端一处**：新增 `link_pair_info`（问一句「屏幕上该摆哪张」，
   一张票挂够 `pair::REFRESH_AFTER=70s` 才换），前端定时器改成**只问不换**（`QR_POLL_MS=15s`）。
   原来两个面板（设置弹窗 + 浮层按钮）各挂一个 70 秒定时器、每次都硬换一张，
   屏幕上摆的很快就不是当前那张 —— 这是 race 的主放大器。`link_pair_qr` 只留给「换一个码」那颗按钮。
2. **正有设备在握手时不许换码**：`LinkState.pairing_busy`（`PairingBusy` RAII 守卫，早退路径自动摘），
   `link_pair_qr` / `link_pair_info` 撞上它就把当前那张原样给回去（不是失败 —— 屏幕上还是那张能扫的）。
3. **失败要能照着做**：桌面按模式把原话包起来（Pair → 「配对码和电脑上当前这张对不上了：请在手机上
   扫屏幕上现在这张码」；Reconnect → 「这台设备两端的配对记录不一致：请在桌面上重新配一次」），
   手机侧同理（「没连上：请在电脑上扫屏幕上现在那张码（原话）」）。原话留在括号里，不抹线索。

验收：`cargo test --lib` 184 例（+1：`该不该换码只由窗自己判`）、`npx vitest run` 1188 例
（`DeviceLinkSection.qr.test.tsx` 整组按"只问不换"重写：定时器问 5 次而 `pairQr` 一次都不许调、
服务端说该换界面才跟着换、连着时连问都不问、手动那颗才是换码）、`tsc` 干净。

上机复验（模拟器 x86_64 debug ↔ 本机 dev 桌面）：
- **守卫是确定性的**：用一个「连上但不发 hello」的裸 TCP 连接把桌面卡在握手里，这期间连点
  `link_pair_qr` 与 `link_pair_info` —— 票 `18d166cf` 一动不动；把那条连接掐掉再点，立刻换成
  `51ae081a`。用「手机发一次配对、桌面 80 ms 后换码」来测是测不出来的：那次握手 80 ms 内就被
  一个 RST 打死了，守卫随之释放，看着像没生效（差点把这条判成 bug）。
- **他的顺序走通**：桌面点「刷新配对码」→ 手机照屏幕上这张配 → 连上并落到「电脑上正打开的文件」。

**顺带一条会咬人的**：新加一个 tauri 命令，光在 `lib.rs` + `build.rs` 注册还不够，
**必须同时进 `src-tauri/capabilities/default.json`**（权限名是 `allow-link-pair-info` 这种连字符形态）。
漏了它，前端那次 `invoke` 报 `not allowed` —— 而互联面板里的取码是 `.catch(() => {})` 静默兜的，
表现成「二维码根本不出现」，一点也看不出是权限。这次是**在真机/模拟器上点出来的**，`tsc` 与单测全绿。
顺手把 `allow-link-pair-approve` / `allow-link-pair-deny` 两条（命令已随 TOFU 一起删掉）从清单里摘了。

**教训（下一轮别再犯）**：把"只有用户主动才会发生"的状态变更改成后台定时行为之前，
要先问一遍**还有谁在依赖它的旧不变量**。这里依赖的是"当前那张 == 屏幕上那张"，
而依赖方是两条不带标识的旧口 —— 新口自己没事，所以单测与前端实测全绿，只有真机手动流程撞出来。

#### 2026-09-27 第二次：他手机上那句「对端已关闭连接」的另一半根因

他装上带 race 修复的包再扫，还是「对端已关闭连接」，界面上那一屏（自动落地的改进生效了）把这句原话摆了出来。
这次桌面侧有 250 ms 采一次的时序：

```
19:16:24  桌面 lastError = 帧解密失败：配对票不匹配，或链路已被截断   ← 没有我加的那层前缀
```

**没有前缀就是线索**：那句是 `run_pump` 里的 `mark_error` 发的，不是握手阶段的 ——
说明握手成功、桌面已经 publish connected 并建好监听，**紧接着第一帧解不开**。和票无关，是会话层面的。

顺着这条查出一个更基本的缺陷（这条是确凿的、可复现的）：

```
手机 status.peerKeyId = a4f9e74f…   ← 这次会话真正的 keyId
手机 prefs.keyId      = b8e5535d…   ← 偏好里记着的，是上一次的
桌面配对列表里没有 b8e5535d
```

`rememberPeer(st)` 一直挂在**发起连接那条命令的返回值**上，而 `link_client_pair` /
`link_client_reconnect` 这类命令在握手完成前就返回了，那一刻的快照里 `peerKeyId` 还是空串
（`rememberPeer` 自己判空、直接 return）。于是偏好里的 keyId **永远慢一次配对**：
下次启动的免扫重连拿一个桌面已经不认的 keyId 去撞 → 报「这台设备未配对或已被移除」，
而这条注定失败的旧连接又和用户紧接着扫的那一次撞在一起 —— 两端各有一条活连接在握手，
正是「握手成了、下一帧解不开」这种形状的来源。

改法：**记对端只认状态推送**。App 里加一个手机侧的 `subscribeLinkStatus(s => rememberPeer(s))`，
扫码 / 粘贴 / 短码 / 免扫重连四条路一次覆盖；`run()` 与 `ScanLinkEntry` 里那两处"在命令返回值上记"
删掉（它们看着像在工作，实际每次都是空转）。`rememberPeer` 本身没错，错的是喂给它的时刻。
钉成 `link.test.ts` 两例：`peerKeyId` 为空时一个字都不写、带上才记且从 `peerAddr` 拆出 host/port。

验收：`npx vitest run` 1190 例、`cargo test --lib` 184 例、`tsc` 干净；
模拟器上「配对 → 重启 App → 免扫重连自己连上」已复验（`status.keyId` 与 `prefs.keyId` 都是 `01a9484c`，
重启后没人扫码就 `connected=true`）。

#### 2026-09-27 第三次：「已经连着的时候再扫一次」把旧连接拆了

上面那条修完，他手机上还是同一句「对端已关闭连接」。这次两侧时序合起来才看清：

```
19:35:57.418  桌面 connected=true   （启动时免扫重连成功）
19:35:57.949  桌面 connected=false  （0.5 s 后 —— 用户在这之前又扫了一次）
手机：connected=false  err=握手写出失败：Connection reset by peer (os error 104)
```

**扫码 = 再拨一次**，而拨之前手机会先拆掉手上那条活连接。拆与拨之间只有几十毫秒，
新连接的 SYN 撞上桌面侧那条还没散掉的旧 socket → 对端回 RST；旧连接的读循环还可能收到
新连接的密文，于是桌面报「帧解密失败」、手机报「对端已关闭连接」—— 同一次事故的两张脸。
也就是说：**用户多做一次"连接"，反而把已经好的连接弄断了。**

先试的是「拆完等 600 ms 再拨」（前端 `link.ts` 里），**压不住**，实测照样 RST。
真正的做法是**同一台就别重拨**，而且这道闸要放在 Rust 的 `start_client` 而不是前端的包装函数里 ——
放在前端时我用 CDP 直发命令"测不出修复"，恰好说明还有别的调用方能绕过它。
判"是不是同一台"用 `peer_addr == host:port`（重连与配对两条口都带地址；这一刻 keyId 可能还没派生出来）。

模拟器复验（三条都要过）：
- 连着同一台再扫 → 命令直接返回 `connected=true`，旧连接不动，5 s 后仍 `connected=true` 无报错；
- 主动断开 → 再扫 → 正常重新配对，拿到新 keyId `ea07f355`；
- 启动免扫重连 → 自己就连上（上一条已验）。

**教训**：这类"两个连接抢同一个四元组"的问题，等时间是等不掉的，只能不制造第二次连接。
判据放在能被绕过的层，就等于没有 —— 用**绕过 UI 的调用**（CDP 直发命令）验一遍，
才能看出守卫到底在哪一层生效。

#### 2026-09-27 第四次：他按下电源键，链路就没了 —— 以及它背后那个把偏好写坏的 bug

他确认了断开的时机：**按电源键息屏**。安卓挂起 Wi-Fi 栈，手机这条 TCP 客户端连接被系统直接销毁
（桌面在 14 秒后收到 `os error 10054` 的 RST，手机进程还在、不是崩溃）。这条链路不做后台常驻
（项目「轻量」那道门槛），所以正确做法不是保活，而是**掉线了自己接回来**。

第一版接法挂在 `document.visibilitychange`（亮屏回前台）上 —— **WebView 里实测不触发**，
按 HOME 再切回来连着等了一分钟也没重连。改成不依赖生命周期事件：以"掉线"这个状态本身为触发点，
`startLinkKeepAlive()` 订着状态推送，`role==='client' && !connected` 就按 **10 / 30 / 60 秒**退避重拨，
连上立刻停表；用户主动点「断开」时置 `userClosedLink`，自动接回不覆盖他的决定。
退避是必需的：桌面那边心跳 15 s × 2 才发现上一条死了，在那之前它谁都不接（回 `busy`）。

用 `svc wifi disable/enable` 掐网络复验时，暴露出**第三个** bug（也是"息屏之后再也连不上"的真凶）：

```
prefs = {"host":"","keyId":"f2258c94…"}   →  重连命令报「地址不能为空」
```

`mark_error` 清 `peer_addr` 却**不清 `peer_key_id`**，于是掉线那一刻推出来的状态是
"有 keyId、没地址"的半成品；而上一轮刚把"记哪台设备"改成跟着状态推送写 —— 它忠实地把这个
半成品写进了偏好，之后每次免扫重连都撞「地址不能为空」，只能重新扫码。两处一起修：
`mark_error` 里 `peer_key_id` 与 `peer_addr` 同生同死；`rememberPeer` 两个字段都齐才落盘
（钉成 `link.test.ts` 一例：只有 keyId、地址为空时一个字都不写）。

**教训**：把"在某个动作的返回值上记状态"改成"跟着状态推送记"是对的，但状态推送里**每一种组合都会来**，
包括错误路径上那种自相矛盾的半成品。加订阅写持久化的同时，必须给写入端加"这条完整吗"的判据，
并且把清理路径（`mark_error` 这类）和被清字段一起对齐 —— 少清一个字段，就是一条把偏好写坏的路径。

#### 2026-09-27 第五次：他一句「不需要防得那么死」—— 我加的闸门把功能自己锁死了

他息屏超过一分钟后再看：**两端各一颗灰点，怎么扫都连不上**，桌面「上次失败」停在
「帧解密失败：配对票不匹配…」。查下来是上面那两道我新加的东西叠出来的死循环：

- 手机按退避一直重试（这是对的），但桌面**一上来以 `busy` 拒第二条连接**，
  而它自己还要等心跳（15 s × 2，最长 45 秒）才发现旧那条已经死了 → 这段时间手机每轮都撞 `busy`；
- 撞回来的失败被**失败限速**记了账，攒够 5 次就把手机 IP 关在门外 60 秒，出关后继续撞、继续记账
  → **正常操作被当成攻击处理，功能自己把自己锁死了**。

两处按他的判断放宽（他 owns "防到什么程度"，这一条是他定的）：

1. **新连接认证成功后直接把旧的顶掉**，不再以 `busy` 拒。挡在门口的仍然是凭证
   （128 bit 的票 / 已配对的 LS），谁出示得对谁进来。为此把「停止位 + 推送队列」捆成
   `Live` 交给每条连接自己持有：被顶掉的旧线程还在它 20 ms 一轮的循环里转最后一圈时，

   表现成"刚连上就掉"。收尾（清 push / 重建监听 / 报 disconnected）也只在"我还是当前那条"时做。
2. **失败限速只数 6 位短码那一种口**（`PairingWindow::slot_is_code`）：票与 LS 都猜不出来，

   一律不进闸门。

#### 2026-09-27 后半场：交接为什么静默失效，以及他接着点的四条（下一会话从这里接）

**根因一句话**：交接那份「这次连上了要交接」的意图，活不过宿主（`App`）的一次普通重渲染。
`useLinkHandoff` 把 `arm/finish` 写进了订阅 effect 的依赖，而 `useT()` 每渲染给一个新的 `t`
→ 依赖每轮都"变了" → 每次重渲染都退订再订阅，而退订的清理顺手 `drop()` 掉了意图。
顶栏「扫一扫」扫到码第一件事就是 `onOpenChange(false)` 收相机 —— 那是 App 自己的一次 setState，
必然排在 `connected` 事件之前。**所以扫码这条口从上线起就没通过**，而设置页里点「连接到 MISAKIMIKU」
那条不触发 App 重渲染，昨天平板壳的实测正是走的那条，于是侥幸是绿的。

**修法两处**：订阅 effect 只依赖 `enabled`，`arm/fail/finish` 从一份每轮刷新的 ref 里取；
退订只停自己的超时表，不碰用户那一次点按留下的意图。`useT` 改为按语言记忆（`useCallback([lang])`），
它出现在十几处依赖里，不止这一个坑。

**他自己扫了一次码，实测过了**：桌面正看着那份摊到前台、桌面两份干净的进标签条、
脏的那份按设计不接、顶栏换成带绿点的状态钮（`connected=true peer=NOH-AL00 keyId=c21de657af9121b0`，
配对时刻 17:52:47）。

**接着点的四条**：

1. **顶栏那颗改成三副样子**：没连着也没在接 = 扫一扫；**正在自己接回来 = 转圈**（点下去进
   「设置 · 设备互联」，不开相机）；连着 = 状态钮。转圈多久按他定的**跟着整套退避节奏**
   （2+5+10+30+60 ≈ 107 秒），跑完回扫一扫带灰点 —— 但后台仍按 60 秒一档继续试，
   **图标变回去不等于放弃**。信号在 `link.ts` 的 `linkRedialSnapshot/subscribeLinkRedial`，
   由 `startLinkKeepAlive` 写；「有 `peerAddr` 没 `connected`」那一段也算接回中。
   顺带：用户点过「断开」之后 `arm()` 直接不排那一枪（旧写法会先亮 2 秒转圈，说的正是反方向的话）。
2. **连着时那一格只说「设备已连接」**，别的说明一律不要。同时把面板里**留着的那一张旧码**也收掉：
   以前面板开着的时候来了一条连接，那张已经扫不动的码会继续摆着。
3. **防火墙那句改口**：`link.rs` accept 循环里那句「端口已开但没有任何设备来过」的计时从 bind 起算，
   而接受一条连接后只清「提过没有」这个位、不重置时间 → 手机一断开（甚至还在连着、accept 空转到
   下一圈）它立刻又亮，和「已连接：NOH-AL00」同时摆在屏幕上。改成**本次监听进过一条连接就不再回来提**
   （那段注释本来就是这个意思）。实测：连着时 `firewallHint=false`，手机息屏走掉之后仍然 `false`。
4. **交接的触发从「只有用户主动」改成「每一次 connected 都跑，一条连接只跑一次」**：
   冷启动免扫重连、息屏亮屏后自动接回，都该把电脑上正看着那一份摊开、把那棵树换过来。
   区别只在**说不说话** —— 只有 `begin()` 立起的那一次会报失败/超时/接不过来，后台接回的几次一律安静。
   手机上已经开着的那一份走新的 `reveal`：只切前台，一次磁盘都不读（`openPathIntoTab` 对已存在的标签
   会用磁盘内容盖掉它，脏的那份就没了）。

**这一轮又撞出一个冷启动缺陷**：手机上那棵树虽然换成了桌面那棵，却停在一句红字
「手机上还没有连着桌面」—— 因为**树比链路先去列远程根**，那句说的是两秒钟前，然后就一直留着，
得用户自己想到点刷新。现在链路接回来时如果那棵树带着这种时机性的错就重列一次
（`treeHasError` + `subscribeLinkStatus`）；树本来是好的就不动，免得把他展开的层收掉。

**远程树根不再显示 keyId**：裸根 `hide-remote://<设备>` 的尾段就是那串十六进制，名字只有桌面知道，
所以随 `list` 一起报回来（`rootName`）—— 不单开一条命令（树要显示根节点本来就得先列一次根），

#### 2026-10-04：扫一扫转圈很久 + 桌面卡片闪烁 —— 握手那份缓冲区被泵丢了

他报的形状：安卓打开软件后那颗转圈很久才停，桌面重开共享期间两端互联卡片一直闪，好一阵才连上。
两端日志对起来是同一场事故的两张脸：

```
桌面 16:55:52  连上了：NOH-AL00 · reconnect · 握手 13 ms · keyId f3bc178a…
桌面 16:55:52  失败：帧解密失败：配对票不匹配，或链路已被截断
桌面 16:55:52  这条连接结束：… · 连着 0 秒
手机 16:55:52  连上了：MISAKIMIKU · reconnect · 握手 29 ms · keyId 74213e81…
手机 16:55:52  失败：对端已关闭连接
```

**`连上了` 那一行本身就排除了票**：`serve_conn` 里它要等对端的 `Pong` 解密成功之后才发，
所以两端密钥同源、握手是走完了的 —— 死的是**握手之后第一帧**。这跟 09-27 第二次那条
「握手成了、下一帧解不开」是同一句形状，但根因不是配对记录，也不是两条连接抢四元组。

**真根因：一份 `Framer` 就是一条连接的读取进度，而泵另起了一份。** 手机在握手完成那一刻连着写出
`Pong`、`Ping`、第一条请求，局域网 + `TCP_NODELAY` 下这几段字节常在同一次 `read()` 里到达；
桌面为等 `Pong` 的那次读取把这一把字节全取进 `Framer.buf`，`take_frame` 只交出去 `Pong`，
`Ping`/`Req` 的尾巴还留在那份缓冲里。`run_pump` 开头那句 `Framer::default()` 把这份缓冲丢了，
泵下一次从帧体中间开始解析 —— 于是报出来的是「帧解密失败…」，
或者当切点正好落在长度前缀上时「对端帧超过 766314055 字节上限」（日志里那三条巨数就是这么来的，
那是密文字节被当成长度前缀读出来的数）。桌面随即断开，手机只看见「对端已关闭连接」。
**手机侧同一处隐患也在**：桌面进泵先发 `Ping`，它与 `Auth` 挤在同一次读取里时，手机丢的是一整帧
（少一次心跳，看着无害），若那一刻桌上还挂着推送就会丢半帧，报的方向反过来。

**为什么转圈很久、卡片一直闪**：`LINK_RETRY_MS` 的第一档是 2 秒，而退避的计数在
`connected === true` 时归零 —— 每次「连上 0 秒又被掐」都把它归一次零，于是手机永远停在最快那一档，
每次失败都把桌面的 `connected` 推上去再抹掉，两端的卡片同频闪。日志里 16:55:33–16:58:53 那一大串
两秒一次的尝试就是这个循环，中间 16:55:54 那次侥幸成功（三帧没挤进同一次读取）连上活了 86 秒。

改法（一处接线，两端同享 —— 这是共用 Rust 层，桌面与 APK 都要重新构建）：
1. `run_pump` 收下**握手那一份** `Framer` 作入参，函数体内不再 `Framer::default()`；
   两个调用点（`serve_conn` / `connect_and_pump`）把各自握手的份传进去。参数没有默认值，
   再想换一份就得同时改两处调用点，不会静默复发。
2. `Framer` 的文档补上「一份就是一条连接的读取进度」这条不变量，以及它破了之后那两句报错的形状。
3. 钉子测试 `握手时读进来的余量归这条连接`（`link/tests.rs`）：三帧一次读入、第一帧收走后
   余量必须还在同一份 `Framer` 里，另起一份则一个字也读不出来。

门禁：`cargo test --lib` 189 passed / 2 ignored（+1 即这条）。`tsc` 与前端测试未涉及（没改 TS）。

**没做的一条，等他定**：`connected` 一闪即灭就把退避计数归零，等于给"连上 0 秒"这种失败开了无限快档
重拨。可以改成「连着超过一个心跳才认这次成功」，但那是他的节奏口径（他要的是掉线马上接回来），
根因已断，先不动。

#### 2026-10-04：手机上写好的东西存进电脑那棵树（`create` / `mkdir`）

**要解决的问题**（他点名）。阶段 2 交付的 `write` 只能改**桌面上已经存在**的文件：内容是从桌面
`read` 来的，所以有基线可判。手机上新写的一份东西、或者想把手机里那份笔记搬到电脑上，
这条路走不通 —— 桌面上还没有那个文件。堵在两处，两处都是设计如此而不是疏漏：
`roots::resolve_rel` 以 `canonicalize` 为权威，而**还不存在的路径必然 `NotFound`**；
`fsrv::write` 又要求基线必填并先读一遍旧文件。于是「存不进去」在界面上表现为
一句 `notfound` 或 `badparams`，听起来都像链路坏了。

**他要的形状**（2026-10-04 定，推翻了我提的"在电脑树里长按新建"那一版入口）：
保存时（新建的文档首次保存、以及另存为）在**文件名那一层**里选目的地 —— 本机 / 已连接的桌面端；
没连桌面时这一排根本不出现（那种情况只能存本机）。选桌面端就打开一个文件夹树选择弹窗，
复用已经做好的树那一套行样式。落点因此是"目的地与名字同一次问清"，不多一层窗、也不多一步。

**协议面（两端共用的 Rust 层，出包要两端都出）**
1. `roots::resolve_new(root, rel)`：新建那条路。父目录照老规矩走完整四道
   （字面拒绝 → join → canonicalize → 组件级根内校验），名字当**单段**附加，
   因为 `check_rel` 已保证段里没有分隔符与 `..`。能出去的唯一可能是父目录本身外指，
   而那正是父目录那一次 canonicalize 挡住的。
2. `fsrv` 新增 `create` / `mkdir` 两条方法。`create` 的三种回话：建成（回哈希，可直接当基线用）、
   `exists`（位置被占，一个字没写，带回占着那一份的哈希与尺寸）、`conflict`（用户选了覆盖，
   但桌面在"问"与"写"之间又改过 —— 交回去的基线就是为这一眼存在的）。
3. **`@w/…` 白名单引用不能当新建的落点**（`badpath`），新建只认共享根；与 `resolve_in_scope`
   同一条规矩：`@w/…` 绝不退回按根内路径再试一次。
4. `mkdir` 只建一层（`create_dir`，不是 `create_dir_all`）：目的地该是树里列出来的那一层，
   一路静默长出三层等于把「这条路径写错了」变成「桌面上多出几棵树」。

**三条按产品口径定下来的写法**
- **同名绝不静默覆盖**。`create` 撞名回 `exists` + 那一份的哈希与尺寸，手机上那句是
  「电脑上已经有同名的这一份（12 KB）。改个名字，或覆盖它。」—— 与 `write` 的基线判定同一个立场：
  桌面上那份不是我们建的。用户点覆盖时把刚回的哈希交回去。那份超过 6 MB 上限时哈希给空串，
  于是**「覆盖」那颗按钮根本不出现**（摆出来也点不通：桌面拒收没有基线的覆盖）。
- **桌面不为「写入」单独加授权**，沿用现有共享开关 + 明示（他的口径：便利优先，风险用可见状态补回来）。
  `LinkShareChip` 那句「手机可访问 · <根>」本来就说的是这件事，不加第二颗开关。
- **远程行上那几个协议里根本没有的入口不摆，而不是灰着**：重命名 / 删除 / 剪切复制 / 粘贴 /
  复制路径 / 在文件管理器中显示。灰着也要人猜为什么，而这一档是根本没那条路。
  `fileOps.ts` 里同时拦住（`unsupported`，**永久**码，绝不进 `LINK_DOWN_CODES`），
  因为手机上真正该拦的是判据顺序 —— 见下面那条真 bug。

**查出来并修掉的一条真 bug**：`fileOps.ts` 的四条 `fs_*` 封装都是**先问 SAF 桥再问别的**，
而安卓上 `HeidBridge` 一直存在（它是设备能力，与"这条路径属于谁"无关）。于是手机上把那台电脑
当文件夹树打开、长按 → 新建文件，`hide-remote://…` 被送去 `createInTree` 拆 `treeUri\0相对路径`，
拆不出来返回 null，界面上是一句「操作失败：SAF create rejected」——
既不是原因也不是用户能做的事。现在远程分支判在桥之前，`fsCreateEmptyFile` / `fsMkdir` 走链路命令，
`fsRename` / `fsDelete` / `fsCopy` / `fsReveal` 对远程路径当场拒。

**按实测改掉的一处口径**：`resolve_new` 起初只 canonicalize 父目录，于是 `readme.md/new.md`
这种"拿文件当父目录"的写法解析成功（`canonicalize` 对文件也成功），最后换来一句
「写入失败：…」——不是逃逸（拼出来仍在根内），但手机上那点保存撞到只会以为链路坏了。
补一道「父目录必须是目录」（`badpath`，一句「新建条目的上一层不是文件夹」），
测试 `新建的父目录不存在或不是目录时明确拒绝` 先红后绿。

**落盘之后的可见性**：桌面自己那份递归监听会推 `event{fs}`，手机上的树只重列受影响那一层，
建出来的文件随即出现在树里；选择抽屉里也立刻看得见。

**门禁**：`cargo test --lib` **209 passed / 2 ignored**（roots +6、fsrv +13、
`远程命令走完整加密链路往返` 那条真实 TCP 里补了 mkdir→create→同名→覆盖→冲突→根外新建被拒六笔）、

## 明确不做（守住"轻量"）

插件系统、LSP/智能补全、内嵌终端、Git 集成、账号与云同步、主题市场、AI 面板常驻、
电子表格能力（公式 / 多 sheet / 单元格样式）、跨文件批量替换与宏录制。
—— 需要这些的用户有 VS Code；H.I.D.E 的目标是"秒开、约 7 MB、够用的编辑器"。

关于「账号与云同步」的边界（v1.5 之后需要讲清，否则看着自相矛盾）：**不做的是账号体系与云中继**，
v1.5 的设备互联是**局域网内两台设备直连**——无账号、无服务器、内容不出局域网、开关关闭即完全释放端口。
两者不是一回事。设备互联自己的「明确不做」清单（实时协同编辑 / CRDT、跨公网穿透、手机当服务端、
自动三方合并等）见设计稿第 15 节。

另：以下两条经查证属于**有意妥协**而非待补的缺口，不要再当遗留项重提——

- **平板标签关闭钮维持 28×28**：标签内扩到 48dp 会压到邻标签，替代出口是长按标签弹菜单。
- **实时协同编辑 / 两端同时持有同一份未保存内容**：会产生「说不清哪边是对的」的状态，
  v1.5 的语义定为「移交」（所有权转移）而非「同步」。

## 优先级依据

1. **打开文件这条路径优先**：大文件、乱码、换行符、找不到内容 —— 这四项决定用户第一分钟的去留，v1.2 全部收口。
2. **再补桌面顺手度**：跨文件搜索、打印 / 导出 PDF、十六进制查看，都是"平时不用、要用时必须有"的能力，且都不需要常驻进程。
3. **然后是内容格式深度**：Markdown / CSV / SVG / 图片已经把优势立起来，JSON / YAML 与打印是顺着同一逻辑的延长线。
4. **多平台与 AI 放最后**：两者都会显著增加维护面或包体积，且都不是当前用户停留的原因；先给结论（做 / 不做），再谈实现。
   —— 多平台的结论已在 v1.4.1 条目 40 给出：**不做**，Windows + 安卓单平台做深（依据见该条）。AI 仍留在 v2.0。
5. **设备互联排在触屏收尾之后、AI 之前**：它解决的是「同一个人在两台设备上被割裂」这个真实痛点，
   比 AI 更贴近编辑器本职；且它**大量复用既有机制**（`DirLister` 抽象、`SessionState` 载荷通路、
   `jumpRequest`、diff 时间线、递归监听、编码检测链），新增依赖极少，与「轻量」定位不冲突。
   但它引入网络与并发状态，维护面显著大于此前任何一版，故单独成一版、不与其他主题混挂。
