默认端口 47123，测试配对档开着（这条路上没有人点「允许」）。

WiFi 一律 `adb shell svc wifi disable / enable` 真断真恢复，不用代码模拟；

## 1. 断连时保存：1 秒内落进队列，不是等满 30 秒

在线打开 `README.txt` → 追加一行 `OFFLINE-WIFI-OFF` → 关掉 WiFi → 点保存。

| 观察项 | 结果 |
| --- | --- |
| 关掉 WiFi 之后的路由 | `ping 192.168.31.87` → `connect: Network is unreachable` |
| 点保存到出现提示 | **1 秒** |
| 提示原文 | 「已离线保存到手机，等待同步」 |
| 标签页 | 保持脏，内容一个字没动 |
| IndexedDB `heid-offline/writes` | 1 条：`b8e5535d/README.txt` 状态=queued 字符=206 CRLF=否 基线=cda8df31 试过=0 |

为什么不是 30 秒：套接字在 WiFi 关掉那一刻就报错，泵的 `Conn::shutdown` 把所有在飞的请求
当场唤醒并回 `dropped:` —— 30 秒超时那一档只在「对端静默但不报错」时才会碰到
（笔记本合盖、信号边缘）。两种都算链路级失败，都在 `LINK_DOWN_CODES` 里。

顺带复验了在线那一条通路：同一次会话里先做了一次在线保存，桌面上 `README.txt` 尾部
确实出现 `-viaExec`，手机上没有出「离线」提示。

## 4. 重连之后：一致就静默写回，桌面动过就标红请人裁决

**成功那一支**（桌面上没动过这个文件）：把 prefs 里的设备记好后冷启动 → 免扫重连
`role=client connected=true peer=MISAKIMIKU` → 队列 0 条，桌面 `README.txt` 尾部
出现 `-viaExecOFFLINE-WIFI-OFF`（手机上断网期间打的那一行原样落到了桌面）✓
基线没变过（6232f43c 一路带着），所以判成「一致」不是判成「冲突」。

**冲突那一支**（断连期间桌面也改了）：在同一份文件上追加一行 `DESKTOP-EDITED-WHILE-PHONE-WAS-OFF`，
WiFi 恢复 → 免扫重连 → 回放撞上线上的基线判据：

| 观察项 | 结果 |
| --- | --- |
| 队列条目 | `状态=conflict`，`试过=1`（后来一轮是 2） |
| 桌面文件 | 尾部仍是 `DESKTOP-EDITED-WHILE-PHONE-WAS-OFF`，**手机那份一个字都没盖上去** |
| 树顶横幅 | 「有 1 处需要你确认」 |
| 那一行 | 红点，`aria-label="需要确认"` |
| 通知卡片 | 同一句「有 1 处需要你确认」（不是「同步失败」） |

标签没开着（重启后远程标签恢复不了），所以这次只标红、没有把差异塞进时间线 ——
与单测里钉的那条一致：时间线的存活域是被标签引用的路径，没开着就假装给出一份看不见的差异更糟。

**折叠在设备上的样子**：在已经有一条 `conflict` 的同一份文件上再离线保存一次，
条目变成 `状态=queued 字符=280 基线=6232f43c 试过=1` —— 内容取最新，
基线与尝试次数都保留旧的那份，正是条目 44 要求的折叠形状。

## 6. 查出来的真问题：重新配对之后，攒的那份永久卡住而且不吭声

第一轮回放在手机上跑不通：WiFi 恢复、重新配对成功、桌面 `README.txt` 却没有那一行，
队列里那条还在，`attempts=0`（**一次都没试过**）。

根因不在回放逻辑，在设备键的形状：`LinkStatus.peerKeyId` 是**那把 LS 的哈希**
（`pair::key_id`），而每次配对都会重新生成临时 X25519 → LS 变 → keyId 变。
免扫重连复用存下来的 LS 所以 keyId 稳定；**重新配对**（用户连不上时最自然的那个动作）
会换一个新 keyId。离线条目按 `deviceId` 分台，于是那几条变成"属于另一台电脑"，
`forDevice()` 一条都不放 —— 逻辑没错，但界面上完全静默。

实测两次的 keyId 就是证明：第一次配对 `b8e5535dfd43a59b`，第二次 `4f7ca381ee336f19`，
同一台电脑、同一个共享根。

判据保留（连着 A 就不能把 B 上攒的改动写进 A 的同名文件，这是条目 44 的原话），
改的是**不许默默卡住**：一连上就出一条「有 N 份是攒在另一台电脑上的」，
说清「连回原来那台之后会自动补上」。同一趟连接只提一次，不当每帧的唠叨。

代价如实记：没有动协议去把设备键换成长期身份指纹（那是 `§12.1-5` 那个 fp 的活），
所以「重新配对而不是重连」这条路上，用户仍需要连回原来那台。要做成"换键也能认出来"，
得让 `hide-remote://` 的 deviceId 改用长期身份指纹 —— 那件事记在 ROADMAP 的欠账里。

## 7. 工具账

- **`adb shell input text` 打不进 CodeMirror**：连着两轮都失败（焦点确实在 `.cm-content` 上，
  字就是进不去），CDP 的 `Input.insertText` 报 `inserted` 也没有落地。
  能用的是页面里的 `document.execCommand('insertText', …)` —— CM6 靠 DOM 观察接住它，
  走的是与真实输入同一条 `updateListener` → `updateTabContent` → 脏标记的路。
  `scripts/cdp-audit.mjs` 因此加了 `--port=`（9222 手机 / 9223 桌面）。
- **`link-lan-check.mjs` 的 `offline` 子命令**：只读队列与清队列两件事，**不提供写入** ——
  往队列里塞东西就等于用代码模拟断连，而这一版的判据恰恰是「真拔网线之后内容还在不在」。
- **配对工具不会写 prefs**：`pairtest` 走 `link_client_pair_code` 命令面，绕过了配对 UI 里
  那句 `savePrefs({keyId, host})`，所以用它连上的设备在界面上没有「连接到 X」那颗按钮，
  免扫重连也不会发生。验重连那条路要么从界面上真配一次，要么先把 prefs 落好
  （本轮用的是后者：把 `heid-link-prefs` 写成配对产生的那份 keyId，再冷启动）。
- **一次自摆乌龙**：第二轮「离线编辑」打到的是 `welcome.ts` —— 冷启动之后远程标签没恢复
  （断连时读不到盘），DOM 里唯一的 `.cm-content` 是欢迎页那个。判据没错，是脚本看错了对象。
  教训与历代同一条：**动手前先确认屏幕上开着的是哪一格**。
- **`svc wifi disable` 之后保存 1 秒就返回**：socket 当场报 `os error 103`，泵的 `shutdown`
  把在飞的请求全部唤醒成 `dropped:`。30 秒那一档要留给「对端静默但不报错」
  （合盖 / 信号边缘），所以两种码都得在名单里。
