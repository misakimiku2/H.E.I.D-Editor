# 超大文件打开策略（v1.2 设计稿）

> 状态：待评审
> 归属版本：v1.2「大文件与跨文件检索」
> 范围：本文只回答一个问题——用户执意打开几十至几百 MB 的文本或表格文件时，H.I.D.E 给什么体验。

## 结论先行

按文件尺寸分三层处理。**第一层（≤ 32 MB）正常打开可编辑**，但把长文档下最容易翻车的两处（查找上限、撤销历史）做顺；**第二层（32 ~ 512 MB）只读分块预览**，内存里永远只有可视窗口，提供一个「提取片段到新标签页」的编辑出口；**第三层（> 512 MB）拒绝打开**，提示改用专用工具。不做外存可编辑——为 0.1% 的场景重写整个文档模型，违背轻量定位。

## 为什么是现在做

大文件路径是 H.I.D.E 被用户遇到的第一分钟问题，也是同类轻量编辑器被抱怨最多的一环。Notepad4 在 2026 年把「移除查找/替换文本长度限制」当作一个版本来修，说明长文档检索是这个品类的长期战场。

当前的边界落在代码里的事实上，逐条列在下面。这些不是推测，全部可以在仓库中定位：

| 项 | 现值 | 位置 |
| --- | --- | --- |
| 大文件降级阈值 | 2,000,000 字符（关闭高亮/小地图/补全/选区匹配） | `src/lib/tabModel.ts` `LARGE_FILE_CHARS` |
| 查找扫描上限 | 2,000,000 字符 | `src/lib/searchCore.ts` `MAX_SCAN_CHARS` |
| 查找匹配数上限 | 5,000 条 | `src/lib/searchCore.ts` `MAX_MATCHES` |
| 拆分历史重扫阈值 | 5,000,000 字符 | `src/lib/searchCore.ts` `RESCAN_DOC_LIMIT` |
| 查找高亮装饰上限 | 5,000 条 | `src/lib/editorSearch.ts` `MAX_DECORATIONS` |
| 撤销历史 | 200 条全文快照 | `src/lib/tabHistory.ts` `MAX_HISTORY` |
| CSV 网格闸门 | 5 MB / 50,000 行（超限退文本视图） | `src/lib/csv.ts` |
| 二进制判定 | 前 8 KB 含 NUL → 只读 | `src/lib/encoding.ts`；Rust 侧 `src-tauri/src/encoding.rs` |

这些边界里真正的约束在 `src/lib/tabHistory.ts:13`：**撤销历史存的是全文快照**（`stack: string[]`，200 条上限）。一个 50 MB 文件连续打字时每 800ms 落一条快照，大约 20 分钟把 200 条填满；之后每次合并更新都会生成一份新的 50 MB 字符串。WebView 的堆在几百 MB 就会紧张——这就是「能开但越用越卡」的根源。

## 三层策略

### 第一层：可编辑（≤ 32 MB）

现在就能打开的尺寸，重点是把降级路径做顺，让用户感知不到断层。

| 关注点 | 方案 |
| --- | --- |
| 打开速度 | 保留整体载入，无新机制。32 MB UTF-8 约 3,000 万字符，读取 + 解码 + CM6 文档构建在 1~2 秒级；不引入流式解码 |
| 查找上限解除 | `searchCore.ts` 改为流式分段扫描（按 256 KB 窗口滑动，窗口重叠保护区避免跨窗口匹配被切断），全量匹配计数；装饰仍最多画 5,000 条（CM6 装饰超几万后每帧渲染开销显著），UI 显示「共 123,456 处匹配（仅高亮前 5,000 处）」 |
| 撤销历史 | 大文件（> 4 MB）自动把 `MAX_HISTORY` 降至 5 条并在状态栏提示；是否迁移到 CM6 ChangeSet 增量（每步只存 diff，内存 O(改动量)）留待自适应降档上线后按实测决定 |
| 小地图 | 已实测（Blink/WebView2 同内核）：canvas 单边上限 65535 设备像素，且越界元素永久失效。据此改为画布高度固定 = 容器可见高度、只绘制可见行窗口（绘制量与行数无关）。成本与文档规模脱钩后，「大文件」（> 200 万字符）也保留小地图与语法高亮：CM6 高亮是视口级惰性解析，实测 12.7MB / 31.5 万行文件打开时语法树只覆盖 0.8%、整篇解析滞留 ≈ 2.3 字节/字符，大文件降级只剩补全/选区匹配/自动缩进与粘性滚动。实现见 `src/lib/minimap.ts` 与 ROADMAP v1.2 第 30 项 |
| CSV | 网格闸门不动（5 MB / 5 万行），超过的 CSV 与普通文件一样走文本视图 + 第一层降级——网格编辑器是全量 DOM 渲染，流式化改造不在本版范围 |

### 第二层：只读分块预览（32 ~ 512 MB）

核心原则：**内存中永远只有可视窗口**。打开时不再整体读入，改为 Rust 侧按字节区间读取并对齐到行边界。

新增 Rust 命令（命名与既有 `read_text_file` 风格一致）：

```rust
/// 探测大文件：文件大小、总行数（预扫）、编码判定
#[tauri::command]
fn probe_large_file(path: &str) -> LargeFileInfo { ... }

/// 按行窗口读取：从 startLine 开始读 maxLines 行（对齐行边界，解码后返回）
#[tauri::command]
fn read_line_window(path: &str, start_line: u64, max_lines: u32, encoding: &str) -> LineWindow { ... }
```

前端体验：

- 状态栏显示「只读 · 分块预览 · 第 12,345 / 890,000 行」
- 滚动到窗口边缘时静默换窗（预读相邻窗口，滚轮不停顿）
- 跳转到行可用：每次换窗顺带记录「窗口首行字节偏移」构成稀疏偏移表（内存开销可忽略），跳转时二分偏移表再顺序补齐；首次定位是一次顺扫，之后 O(log n)
- 文件内查找复用第一层的分段扫描：按窗口顺序流过全部字节区间，跳过已扫过的窗口
- 二进制判定升级为前 16 KB 采样（大文件里 NUL 可能藏在更深处），判二进制则转十六进制视图（v1.2 同批次）
- **编辑出口**：选中文本 → 右键「提取到新标签页」。新标签页是普通可编辑标签，走第一层全部能力，标题注明来源——想改的人只改他关心的那一段
- **没有保存按钮**：第二层没有保存概念，想保存的人请先提取片段

安卓与桌面共用同一套 Rust 命令，只在 UI 呈现上差异（手机无状态栏，改为顶栏 chip 显示只读状态）。SAF 的 content URI 已有 Kotlin 桥（`openTree` / `listTree`），读文件走同一 `read_line_window`。

### 第三层：拒绝打开（> 512 MB）

直接拒绝并给出替代建议。文案草案：

> 这个文件 850 MB，超出了 H.I.D.E 的设计范围（上限 512 MB）。继续打开很可能导致应用无响应——我们不想在占用数 GB 内存和拒绝你之间二选一。
> 若确有需求：klogg（开源日志查看器）、10x Editor（大文件专用）、UltraEdit（商业）、VS Code（会自动降级且可能假死）。

一流的产品会告诉你它为什么不做。拒绝不会让 H.I.D.E 变得更好，但会让用户少丢一次数据。

## 与竞品的分界线

竞品对同一问题给出了三种回答。**VS Code**：超过约 50 MB 逐步降级（关闭语义高亮、简化小地图、关闭补全），200 MB+ 大概率假死或拒绝；**Notepad++**：超阈值弹警告窗，用户可选强制继续，仍属全量载入路线；**Notepad--**：> 100 MB 流式加载，是同类中唯一做「外存可编辑」的，代价是构建面与维护成本明显上升。

H.I.D.E 的答案与三者都不同：**用只读分块预览守住「打开不翻车」的底线，把编辑需求导流到「提取片段」**。放弃的是「全文件可编辑」这个宣传点，换来的是 2.4 MB 安装包和几十 MB 常驻内存不因单个文件暴涨。这是一个立场，不是缺陷。立场的成立依赖边界诚实：如果实测 32 MB 阈值误伤常见文件（如 40 MB 访问日志），应该上调到 48 或 64 MB，而不是私下放行。

32 MB 与 512 MB 的初值依据：32 MB 约 3,000 万字符，是 CM6 全量载入 + 快照历史双重约束下的经验安全线（WebView 堆预算、单字符串上限、Tab.content 与 CM6 doc 双份持有都要算进去）；512 MB 取 10 倍于第一层的数量级安全域，给「几百 MB 的访问日志」留足空间，又不至于让用户对「几百 MB 也能开」产生不现实的期待。

**没做不等于不做**。如果 v1.2 上线后数据表明需要编辑超 32 MB 文件（而非提取片段）的比例不低，那是重新评估外存可编辑的时机。但那个判断有数据再下，不基于今天。

## 落地拆解

v1.2 按四步走，每步独立可验收：

1. **分段扫描**：改造 `searchCore.ts` 为流式扫描，全量计数、限制装饰。验收：200 MB 文本「全部替换」不卡死，替换后保持脏状态。
2. **只读分块预览**：`probe_large_file` / `read_line_window` 两个 Rust 命令 + 前端 `LargeFileViewer` 组件（滚动换窗、跳转、提取片段）。验收：500 MB 文本滚动流畅，峰值内存 < 300 MB（可视窗口 + 预读 + WebView 本底，全部加起来 < 4 MB 的窗口内容不构成压力）。
3. **自适应撤销历史**：`MAX_HISTORY` 按内容尺寸降档（> 4 MB → 5 条），状态栏提示。验收：50 MB 文件编辑 30 分钟，内存增长 < 100 MB。
4. **十六进制视图**：二进制判定改 16 KB 采样，十六进制只读视图复用第 2 步的分块读取命令。验收：800 MB 的 .bin 文件可滚动查看，每行 16 字节。

## 未决问题

三个数值需要评审时拍板：

1. **32 / 512 MB 阈值**：初值依据上文；如实际用户文件分布中 30~40 MB 区间密集，考虑上调至 48 / 512。
2. **跳转首扫成本**：500 MB 顺扫若超过 3 秒，用户会感到「跳转先卡一下」。变通一是接受首次跳转等待并显示进度；变通二是后台预热首扫，代价是打开即占 CPU。
3. **ChangeSet 重构**（撤销历史中期方案）：是否提前到 v1.2 内做，取决于第 3 步降档上线后的实测内存表现；低于 100 MB 增长则不提前。

## 明确不做

- **外存可编辑**：真正的流式编辑缓冲区，为 0.1% 场景重写文档模型。
- **取消第二层、超大文件直接走第一层**：等同于放弃内存底线，让「打开不翻车」失效。
- **首屏先渲染部分内容再后台加载全量**：意味着打开后数秒内文档状态与用户所见不一致，撤销/保存语义都要重写。

## 用户视角的三句话

写代码的人不需要看本文，他们只需要知道：

- 32 MB 以内一切照旧，查找不再有隐藏上限。
- 更大的文件改用只读预览，选中一段可以提取到新标签页继续编辑。
- 512 MB 以上请用专用工具，我们拒绝打开并会告诉你为什么。
