# 扫码器相机手感（v1.5 阶段 1 遗留 → 本轮收口）

> 2026-09-23 建档，2026-09-24 本轮重做。原文记的是「切换摄像头手感」三条遗留；
> 本轮把能自动验的都验了，剩下两条必须人眼/另一台机器的，写在文末「还没了结的」。

## 本轮改了什么

**1. 开流：从「两枪」变「一枪」**（这是「点扫一扫要好几秒才见影子」里我们自己那部分）
- 旧流程：先以 `facingMode:'environment'` 开一颗拿权限 → 枚举 → `tryCandidate(0)` **关掉它再重开** →
  每次开流前固定睡 150ms → 探测黑屏还要等满 1600ms。
- 新流程：有 `localStorage['heid-scan-cam']` 记号就**直接 `exact deviceId` 开那颗**，一次开流定稿；
  只有当开出来的这颗「明显比第一候选差」（前置 / 开不出画面 / 长焦而普通后置在手）才重定向一次，
  **同档之间不再来回重开**。分辨率约束 1920×1080 → 1280×720（解码最长边只用 640，起流更快）。
- 等首帧改成事件驱动（`loadeddata` / `resize` / `requestVideoFrameCallback` + 80ms 兜底轮询），
  出画面立刻返回，不再等满窗口。
- jsQR 预载与开流并行，不排在相机启动后面；`DeviceLinkSection` 挂载时就把 QrScanner + jsQR 两个
  懒加载 chunk 取回来（APK 内资源，不走网络），省掉点「扫一扫」后的 Suspense 空窗。

**2. 切换不再硬切**
- 换镜头前把**屏幕上正显示的那块**（含数码放大后的取景范围）画进一张覆盖 canvas，新流首帧到了再
  淡出 + 轻微放大让位（260ms）。**仍然是串行关旧开新**——两台真机都实测过「同时开两颗会黑屏/HAL 占用」，
  所以没走「先开新再关旧」那条并发路，用冻结帧绕过去。
- 一次切换序列里保留最早那张好画面，逐颗顺延时不会露出黑屏；另有 2.4s 滞留上限兜底，不会永远冻在旧画面上。

**3. 捏合变焦重做**（数学都在 `src/lib/scanCam.ts`，可单测）
- 旧：`目标 = 起始倍率 × 指距比`，线性。1–10× 的量程要把手指真张开十倍才走得完 → 拉到头也没变多少。
- 新：`目标 = 起始 × ratio^(ln(max/min)/ln(3))`，**一次完整捏合行程（张开 3 倍）走完这颗镜头的全部焦段**，
  不同镜头、不同起点的手指行程一致。
- 目标值不再直接下发：每帧做一阶低通（τ=55ms）逼近后再 `applyConstraints`，且同一时刻只挂一份在途请求，
  后到的覆盖先到的 → 手指抖不会灌进 HAL。
- 镜头本身不给 `zoom` 能力时**由数码放大顶上**（预览 `transform: scale()`，量程 1–4×）。
  此时解码只喂放大后那块可见区域（`coverSampleRect` 算矩形，所见=所解），所以数码放大对手指和对二维码都有效。
- UI：中央倍率浮标（捏合时或离开最广端时显示，点一下回最广）+ 底部系统相机式倍率圆片（至多 4 片，
  两端钉住），**替掉原来的变焦滑杆**；换镜头收成左边那颗 `n/N`。圆片/浮标命中区 ≥48dp。

**4. 报错不再误导**
- 按 `DOMException.name` 分流：`NotAllowedError`→权限；`NotReadableError`/`AbortError`/内核自造的一律按**占用**，
  走 0.4s/1s/2.2s 退避自动重试（额度**整次切换共享**，不会每颗各重试三轮变成十几秒转圈），
  额度用尽或每颗都不行才落到「相机暂时用不了」+「重试打开相机」按钮。
  旧版把占用写成「权限被拒（可去系统设置里允许）」，那条文案是错的。
- 开不出画面 / 实测是前置的颗记进 `localStorage['heid-scan-cam-bad']`，下次排序垫底；
  记号镜头若已在坏表里，第一枪就不打它。

**5. 顺带修掉的真 bug**：扫码层被设置弹窗的 `backdrop-blur-xl` 当成了 `position:fixed` 的包含块，
在平板上预览只占弹窗那一格、不是全屏 → 改成 `createPortal(…, document.body)`，层级 `z-[150]`
（高于设置弹窗 100，低于图片预览 200）。

## Tab S8 实测（2026-09-24，签名 release 包 `install -r`）

- 一次开流直落记号镜头：调试行 `BarcodeDetector · 1280×720 · environment · camera 2, facing back · 数码变焦`。
- 这颗镜头确实不给 `zoom` 能力 → 走数码变焦；点 4× 圆片画面真的放大（布纹变糊），圆片高亮跟着走。
- 切镜头 `1/2 ↔ 2/2`、`camera 2 ↔ camera 0` 都成功，没落到报错态。
- portal 修复后预览铺满整屏 ✓。
- **`camera 2, facing back` 与 `camera 0, facing back` 的 label 完全无法区分主次摄**，
  与建档时的判断一致：只能靠「实测朝向 + 坏镜头表 + 扫成功记住」这套，label 排序在这两台上是摆设。

## 一个不是代码的「好几秒」

上一轮在 Tab S8 上授权选的是**「仅限这一次」**，所以每次进扫一扫都被系统权限弹窗打断一次
（录屏实测：弹窗从点击后约 0.7s 出现、停留数秒）。本轮已改选「使用应用时」（`granted=true, USER_SET`）。
**首次真机测试务必先确认这个授权档位**，否则量出来的开流时间全是弹窗时间。

## 第一次进入就落在主摄（2026-09-24 第三次，Mate 40 Pro 实测后）

用户实测：Mate 报出 **6 颗后置**，第一次进扫一扫落在**长焦**（`camera2 6`，扫不了码），
手动切两次才到主摄（`camera2 2`），一到主摄"移到二维码的瞬间就扫到了"。
所以切换按钮从来只是妥协，**真正要修的是开机选颗**。

旧代码错在哪：label 全是 `camera2 N, facing back` 时所有候选同档，
于是「保留 `environment` 随手给的那颗」这条规则把长焦留了下来——它把系统的随机选择当成了判断。

新规则（`boot()`）：
- **有记号**（`heid-scan-cam`）：一枪 `exact` 打开，出画面且非前置就锁定，不探测。常态路径。
- **无记号**：先按 **12MP** 开第一颗并立刻给用户看，同时量它**实际给得出多大**；给得出主摄级就收工
  （常见情况，首次也是一枪，再把同一条 track 降回 720p 预览，不重开相机）。给不出才探：探针同样按
  12MP 要流、只读**交付尺寸**与朝向、**不等画面**，探到第一颗给得出的就停；上限 `MAX_PROBE=6`
  （Mate 报 6 颗后置，上限低于镜头数就可能漏掉主摄，而漏掉之后记号会把错误固化）。
  探测期间调试行显示「选镜头 i/n…」，免得定格画面读起来像卡死。最后结算一次并**立刻记住**。

  **为什么不用 `getCapabilities().width.max`**：华为上它报流配置上限，六颗一个值，分不开（真机失败过）。
  **为什么测量请求必须给到 8K 档**：第二版按 12MP 要流，仍失败——Mate 的潜望长焦**本身就是 12MP 传感器**，
  12MP 请求下它交付 3000×4000，与主摄同尺寸，下限放它过去了、探针一颗没跑（用户截图为证）。
  等于给测量加了天花板。改成 8192×6144 请求后：主摄交付 50MP、长焦只有它自己的 12MP，分得开。
  下限 `MAIN_FLOOR = 16MP` 只作「提前停」的优化；全机器都给不出的老手机探完所有候选、
  **取交付最大的那颗**，不瞎换。caps 与交付尺寸都记进日志（`交付尺寸 {交付, capsMax}`、`探针交付 …`）作对照事实。

- **探测期间不给看画面**（用户实测反馈：定格画面比黑屏更像卡死）。预览在 `state !== 'scanning'`
  或探测中一律 `opacity-0`，界面是黑屏 + 转圈 + 「正在选镜头 {i}/{n}…」，选定了才一次性点亮；
  探测路径因此不再走冻结帧（冻结只留给「用户主动换镜头」那条本来就有画面的路）。
  回归测试 `探测期间不给看画面` 断言中途 `opacity-0` + 进度文案、选完才 `opacity-100`。

- **机型档案**（`MAIN_BY_MODEL`）：探测再便宜也是「首次进入开好幾枪」，而用户会反复重装测试、
  每次都吃这笔账。所以对**真机实测过**的机型直接点名主摄、一次 720p 开流定稿（相机厂商的设备档案思路）。
  种子：Mate 40 Pro（`NOH-AL00`）→ `camera2 4, facing back`（8K 交付测量落在它）。
  运行时校验：档案镜头开不出画面或是前置 → 记一行日志退回探测流，档案错了不卡死也不黑屏。
  优先级：扫成功确认过的记号 > 机型档案 > 8K 交付探测。

- **记号分两种**：`heid-scan-cam`（上次用的）与 `heid-scan-cam-ok`（**真扫成功过**的）。
  只有 `-ok` 确认过的记号才走「一枪」快路径；只有开机写下的记号不作数——它可能是失败探测的产物
  （用户实测就吃过这个：失败那轮把长焦写进记号，下一轮一枪直达长焦），要按交付尺寸重判。
  扫成功那一刻两个键一起写。这样错记会自己纠偏，不需要用户清数据。

出包/装机走 `scripts/android-install.sh`（`install-only` 跳过构建只装现成 APK）：
签名 release + `install -r` 原地升级不丢数据，装完自动 force-stop（不重启进程跑的还是旧代码）。
- 结算失败退回给用户看过的那颗，不留黑屏。
- 回归测试：`无记号且 label 全是通用名` 用 8MP/50MP 两颗通用名镜头，断言开流序列为
  `[长焦, 主摄]` 且记号写成主摄。

## 日志通道：logcat 在华为上不可靠，改走界面内环缓冲

用户按 `adb logcat -d -v time -s HeidScan` 跑，**终端是空的**。原因不是桥没通：
华为/鸿蒙默认压制第三方 App 的日志输出，`Log.i` 根本不进缓冲区
（上一份交接文档里「WebView 的 console 不进 logcat」也是同一个坑，当时归因归错了）。
`HeidBridge.log()` 保留（非华为设备仍可用），但**稳的诊断通道改成界面内**：
`dlog()` 同时写进一个 60 条的环缓冲，点扫码界面那行调试字即可展开、每 0.8s 刷新，截图即可回传。

## 设计更正（2026-09-24 第二次，用户实测 Mate 40 Pro 后）

**用户报**：手机上枚举出 **6 颗摄像头**；在 1× 视图下双指收拢会切到下一颗，切的时候卡一下。
判断是「一般扫码行为就该是一颗摄像头工作，不需要这么多摄像头来回切」——**这个判断是对的，之前思路错了**。

错在哪：把「选对镜头」这件本属于开机内部的事，做成了用户可感知的交互（常驻的 `1/6` 切换按钮 +
捏合到最小继续外拉就换下一颗）。后果是①每切一颗都要重开一次流，那就是他感觉到的卡顿；
②6 颗里绝大多数是微距/深度/长焦，切过去对扫码只会更差；③「拉到头换镜头」是**取景创作**的手感，
不是**扫码**的手感，套错了一个系统相机的习惯。

改法：
- **捏合只管变焦，到量程两端就停**，不再触发任何换镜头。
- 底部**去掉常驻的镜头切换按钮**，只留倍率圆片（1×/2×/4× 或光学那颗的刻度）。
- 选镜头回到开机内部：记号镜头 → 否则逐颗试到「有画面且实测不是前置」为止，坏镜头记进表里垫底，
  扫成功那一刻记住这颗。
- 只保留一个**被动出口**：同一颗上对着扫了 ~8s 仍解不出码，才出现「换个镜头试试」
  （`missRef > 54` 帧；一次开流只提一次，换完镜头重置）。只是提示，点了才走——
  不自动换，因为「暂时没解出码」多半是用户还没对准，上一版就因自动换被坑过。
- 回归测试钉死这条决定：`捏到最广端继续收拢也不换镜头`（给两颗可用后置，捏合收拢后断言
  只发起过一次 getUserMedia、倍率停在 1×）。旧规则下这条会红。

## 三星平板上的两个现象（2026-09-24 用户回报，本轮加了日志待判）

1. **进扫一扫时满屏一个巨大的灰色「播放按钮」占位符。**
   我一度以为是 `screenrecord` 抓不到相机层的假象——**错了，那是真在屏幕上的**（用户直接看到）。
   两个候选解释，本轮的日志就是为分辨它们加的：
   - `video.play()` 被拒 → WebView 会在视频区画这个占位符。已在 `attach()` 里把 play() 的成功/失败
     原样记进日志，并在 `canplay` 时补一次；仍失败则界面直书「自动播放被内核拦下」，
     且下一次点预览区会在**用户手势内**再 play() 一次（那是唯一还能救的时机）。
     注：`setMediaPlaybackRequiresUserGesture` 这条我查过 wry 源码，`autoplay` 默认 true → 该门槛默认是开的，
     所以别照着「WebView 拦自动播放」去改配置，先看日志。
   - 或者那根本不是占位符，而是**某颗后置镜头自己输出的合成画面**（三星把微距/深度颗也报成
     `camera2 N, facing back`，label 与主摄无法区分）。若是这种，`walkFrom` 的「黑屏/无画面才顺延」
     判不住它——它有画面，只是没用。日志里的 `镜头判定` 一行会把两颗的 label/朝向/分辨率都列出来。
2. **在 1× 上双指捏合会「黑一下然后换了相机」。** 这是「拉到这颗最小还想更广 → 切下一颗」的规则在动，
   建档时就是照系统相机的手感设计的。真机反馈说明两个问题：
   - 黑一下 = 冻结帧**淡入**了（`transition-all` 让盖上去也带 260ms 过渡，底下刚关掉的黑名单透了出来）。
     已改成盖上去立刻生效、只有让位时才淡出。
   - 阈值太松：`ratio < 0.85` 时随手一捏就跳。已收紧到 `ratio < 0.7`。

## 测量手段的坑（下次别再踩）

- **`screencap` 在这台 Tab S8 要 3.3 秒一张**（相机层走脱敏路径），亚秒级的黑屏间隙抓不到；
  `screenrecord` 能到 15fps 且画面是真的（前述占位符就是它如实录下来的），但**它录不到相机实时画面**，
  所以「切换期间有没有黑」仍不能靠录屏判。
- `adb shell input motionevent` 在这台只接受单指坐标，**注入不了双指捏合**，别在这上面再花时间。
- 结论：黑屏间隙、捏合手感这两件事只能人眼在设备上看；自动化能验的都放进 `scanCam.test.ts`
  （23 例纯数学）和 `QrScanner.camera.test.tsx`（5 例开流/报错/捏合接线）。


## 收口状态（2026-09-24，两台真机复测后）

**已结**：

- **黑闪与切换卡顿**——用户复测确认没有，并给出因果：这两个症状都挂在「换镜头」这个动作上，
  而扫码改成单镜头、动作本身没了，症状随之消失。冻结帧淡入那个 bug 的修法（盖上去立刻生效、
  只有让位才淡出）保留给「用户主动换镜头」那条路。
- **8K 交付尺寸量主摄**——Mate 40 Pro 实测有效：`camera2 4` 被选中并正常扫上，
  与 12MP 长焦分得开；机型档案命中后首次进入也不再探测。Tab S8 复测无问题。
- **捏合跟手**——用户结论是「**够用，谈不上很流畅，但扫码我觉得应该是够了**」。
  按这句收口，不写成"手感达标"：这两台真机上被选中的镜头都不给硬件 `zoom`（调试行显示「数码变焦」），
  倍率全靠预览 `transform: scale()` + 每帧低通逼近，掉不掉帧取决于当时 WebView 的合成开销。
  真要往"系统相机那种顺"再走，得先量清是 CSS 合成跟不上、还是低通时间常数（τ=55ms）偏黏，
  别凭感觉调参。扫码这个场景不再花这一轮。

- **调试行挂着开流尺寸不重算**（显示 3000×4000 而预览早已 720p）——已抽 `setDbgFromTrack()` 修掉。

**还开着的**：

1. **满屏灰色播放按钮占位符未单独定性**：Tab S8 复测时已不见，最可能就是选错镜头那段时间的产物
   （那颗镜头自己输出的画面）。若再现，展开调试行看 `play(attach) 成功/被拒：<原因>` 一行即可判定，
   别再去啃 logcat（华为上不可靠）。
2. 建档时那条「长焦/广角无法靠 label 识别」仍未解决，只是被降级成不致命：label 在这两台上完全同质，
   判据只剩 8K 交付尺寸与机型档案；真要「认出主摄」得另找代理指标（候选：`focusModes` 有没有
   `continuous`、交付帧率上限）。
